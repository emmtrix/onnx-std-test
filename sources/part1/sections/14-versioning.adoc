[[versioning]]
== Versioning and compatibility

=== Version axes

==== General

ONNX has three independent version axes:

IR version:: the version of the structural and serialization rules given in
<<information-model>>, <<graph-structure>> and <<serialization>>.

Operator set version:: the version of an <<operator-set>>, per <<domain>>, as
published in <<onnx-part-2>>.

Model version:: an identifier assigned by the <<producer>>, opaque to this
document.

[[ir-version-specified]]
==== The IR version this edition specifies

This edition specifies IR version 14.

[IMPORTANT]
.Editorial note
====
IR version 14 is not published. The upstream schema carries it as the current
version with its publication date given as "TBD", and it is the version that
introduces `FLOAT6E2M3`, `FLOAT6E3M2` and the opaque type outside the ONNX-ML
build --- all three of which this document specifies, in
<<reduced-precision>> and <<opaque-types>>.

A standard cannot specify an unpublished version of the thing it standardizes.
Either this edition specifies IR version 13, and those three are removed from
it and held for an amendment, or the Steering Committee publishes 14 first.
The choice is theirs; it should not be made by whichever ONNX release happened
to be vendored when the draft was written.

<<tbl-ir-versions>> is the version history, from the upstream schema.
====

=== IR version evolution

The IR version is a positive integer that increases monotonically.

A change that alters the structure or the meaning of a model, or that breaks a
producer or consumer written against the previous version, SHALL increment the
IR version. A change that does neither SHALL NOT.

NOTE: A change can break a producer or consumer without altering a single octet
of any model — renaming a field of the serialized form is the standard example.
Such a change increments the IR version.

A consumer SHOULD accept a model that omits a field the consumer does not
require. A field that a given IR version requires SHALL be identified as such
in <<annex-schema>>, and a producer SHALL supply every such field.

An increment of the IR version SHALL NOT of itself change any operator set. An
increment of an operator set version SHALL NOT of itself change the IR version.

NOTE: The independence stated above is why this standard is in parts. The IR
version is the cadence of this part; the operator set versions are the cadence
of <<onnx-part-2>>.

[[operator-set-evolution]]
=== Operator set evolution

An operator set version SHALL NOT be changed once published.

An operator is identified by a triple of a <<domain>>, a name and the operator
set version at which that definition of it was introduced. Where the definition
of an operator changes, the changed definition is a new operator with a new
such version, and the previous definition remains what it was.

Where the inventory of an operator set changes, whether by addition, by removal
or by a change to the definition of an operator it contains, a new operator set
version SHALL be published.

<<tbl-breaking>> states the changes to an operator that require a new version
of it.

[[tbl-breaking]]
.Changes requiring a new version of an operator
[cols="4,1"]
|===
| Change | New version required

| Adding, removing or renaming an attribute, including adding an optional
  attribute whose default value reproduces the previous behaviour
| yes

| Adding, removing or reordering an input or an output
| yes

| Adding or removing a type admitted by an input or an output, or changing the
  type of an attribute
| yes

| Admitting behaviour the previous definition did not, under an unchanged
  signature
| yes

| Resolving an ambiguity in the previous definition in favour of what
  implementations already do
| no
|===

NOTE: The third row is symmetric: widening a type constraint requires a new
version of the operator just as narrowing one does. What the previous row's
prohibition protects is the previous definition, which stays available at its
own version.

A model binds each of its nodes to an operator definition by the operator set
version the model imports; see <<operator-set-import>>. How a consumer binds
that definition to an implementation is outside the scope of this document.

=== Compatibility obligations

A consumer that claims support for operator set version stem:[n] of a domain
SHALL accept models declaring any version stem:[m <= n] of that domain, and
SHALL evaluate each node according to the operator definition in force at
version stem:[m].

[IMPORTANT]
.Editorial note
====
The above states backward compatibility as an obligation. Current runtimes do
not universally meet it. Either the obligation is weakened, or it is stated as
written and the gap is recorded in Annex C as a known divergence. The latter is
recommended: a standard states the requirement, and a conformance statement
records what an implementation achieves.
====

=== Deprecation and removal

An operator MAY be marked deprecated in an operator set version. Deprecation
SHALL NOT remove the operator, and a consumer SHALL continue to evaluate
deprecated operators.
